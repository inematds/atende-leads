# Especificação v1 — atende-leads (contrato)

> Testes em `tests/` verificam exatamente o que está aqui. Implementação e testes são escritos a partir deste arquivo, sem combinar detalhes fora dele. Mudança de contrato = editar aqui primeiro.

## 0. O que é

Atendimento de **leads pelo WhatsApp** para um negócio (loja, imobiliária, escola, serviço). Um **agente** responde, tira dúvidas, qualifica o lead e dá uma nota. Quando o lead **pede um humano**, quando o agente **detecta necessidade** ou quando vê **chance de venda**, o sistema abre um **chamado** e oferece o lead ao **colaborador livre há mais tempo**, pelo **Telegram** (privado), com todos os dados e botões **Assumir / Passar / Ligar / WhatsApp**. Ninguém assume no prazo → **alerta 🚨 no grupo** da equipe. O colaborador **fecha** o atendimento com o resultado e volta a ficar livre.

Três interfaces web: **lead** (chat + página "meu atendimento"), **equipe** (painel do colaborador) e **gestor** (painel do negócio). Entrega em **Docker** para VPS, com a Evolution API opcional no mesmo compose.

Python 3, **somente biblioteca padrão** (sem `pip install`), estado em SQLite.

## 1. Execução

- Ponto de entrada: arquivo executável `./atende` na raiz.
- `./atende serve --porta N --dados DIR [--host H]`
  - `--porta 0` = porta livre. A **primeira linha** do stdout é `PORTA=<n>` (flush), impressa quando já aceita conexões.
  - Host padrão `127.0.0.1` (Docker passa `0.0.0.0` pelo comando, nunca no código).
  - `DIR/negocio.json` = configuração (seção 2). Se não existir, copiar `exemplos/negocio.json`.
  - Todo o estado persiste em `DIR/leads.db`. Reiniciar com o mesmo `DIR` mantém tudo.
  - **Segredos de exemplo:** se `token_gestor` for `TROQUE-ESTE-TOKEN` (ou o do `exemplos/negocio.json`) ou algum `codigo` da equipe for igual a um código do `exemplos/negocio.json`, ou se uma integração estiver ligada com o segredo do seu webhook fraco (Evolution ligada com `WEBHOOK_SEGREDO`, ou Telegram ligado no modo `webhook` com `TELEGRAM_SEGREDO`, vazio, com menos de 16 caracteres ou contendo `troque`; ou Evolution ligada com `EVOLUTION_API_KEY` contendo `troque`), o servidor só sobe com host `127.0.0.1`/`localhost`/`::1`. Com outro host (ex.: `0.0.0.0`) recusa: mensagem no stderr com `rode ./instalar-vps.sh ou troque os segredos` e código de saída ≠ 0. `ATENDE_PERMITIR_EXEMPLO=1` libera (só teste/demonstração).
  - Enquanto roda, o `serve` segura uma trava (`DIR/.serve.lock`, `flock`); um segundo `serve` no mesmo `DIR` recusa.
  - **Rede fora do lock:** nenhuma chamada HTTP (Telegram, Evolution, cérebro) nem transcrição de áudio acontece dentro da transação do banco. Envios vão para a **caixa de saída** e saem por um despachante em segundo plano, na ordem, por destino; `GET /api/saude` responde sem esperar o banco. Socket da conexão HTTP com timeout de 30 s. No máximo `ATENDE_MAX_CONEXOES` (padrão 64) conexões atendidas ao mesmo tempo; acima disso responde 503 e fecha — exceto `GET /api/saude`, que responde 200 mesmo com o servidor lotado (healthcheck).
- **Relógio:** `ATENDE_AGORA` (`AAAA-MM-DDTHH:MM`, hora local) fixa o "agora" no início do processo. `POST /api/relogio {"agora": "AAAA-MM-DDTHH:MM"}` [G] muda o relógio em execução **somente se** `ATENDE_AGORA` estava definida no início (senão 403). Sem ela, relógio real.
- **Tarefas de tempo** (ofertas vencidas, alertas, lembretes, retornos, abertura do expediente): `POST /api/tarefas/rodar` [G] roda uma vez e devolve `{"ok": true, "acoes": n}`. Fora do modo `ATENDE_AGORA`, o servidor também roda isso sozinho a cada 30 s.
- `./atende backup --dados DIR --saida ARQ` (cópia consistente do SQLite + `negocio.json` num `.tar.gz`; funciona com o servidor no ar) e `./atende restaurar --dados DIR --arquivo ARQ` — **recusa** (código ≠ 0, stderr com `pare o serviço antes: docker compose stop atende`) se houver um `serve` rodando com esse `DIR`.
- `./atende manutencao limpar-bastidores --dados DIR [--aplicar]` (1.6.8): procura em `info.*` e nas respostas do FAQ do `DIR/negocio.json` as frases com **marca de bastidor** (recado interno: `vendedor informou/disse/falou/passou`, `a base (atual) diz/mostra/informa`, `confirmar com a equipe`, `segundo o vendedor`, `base de conhecimento`, `informação interna`) e lista cada uma (`- info.observacoes: <frase>`, `- faq <id>: <frase>`). Sem `--aplicar` só simula (nada grava). Com `--aplicar`: recusa (≠ 0, `rodando`) se houver `serve` com esse `DIR`; grava backup `negocio.json.<AAAAMMDD-HHMMSS>.bak` (600), remove as frases (item do FAQ que fica vazio sai inteiro) e regrava com permissão 600. Não usa LLM.
- Integrações externas **só** por variáveis de ambiente (seções 15–17). Sem elas, nenhuma chamada de rede sai do processo — exceto a leitura de link que o gestor pede em **Importar de link ou arquivo** (seção 13c, só endereços públicos). Nenhuma URL, chave ou token real no código.

## 2. `negocio.json`

```json
{
  "nome": "Loja Exemplo",
  "token_gestor": "TROQUE-ESTE-TOKEN",
  "url_publica": "http://localhost:8080",
  "horarios": { "seg": [["08:00","18:00"]], "ter": [["08:00","18:00"]], "qua": [["08:00","18:00"]],
                "qui": [["08:00","18:00"]], "sex": [["08:00","18:00"]], "sab": [["09:00","13:00"]], "dom": [] },
  "prazos": { "oferta_min": 2, "alerta_quente_min": 2, "alerta_normal_min": 5, "lembrete_min": 30 },
  "equipe": [ { "id": "ana", "nome": "Ana", "telefone": "5541999990010", "codigo": "ana-1234" } ],
  "produtos": [ { "id": "plano-anual", "nome": "Plano anual", "palavras": ["anual", "plano anual"], "preco": "R$ 1.200" } ],
  "faq": [ { "id": "horario", "perguntas": ["qual o horario de atendimento"], "resposta": "Atendemos de segunda a sexta, das 8h às 18h." } ],
  "cerebro": { "tipo": "regras" },
  "info": { "horario_atendimento": "", "endereco": "Rua Exemplo, 100", "pagamento": "Pix, cartão e boleto",
            "entrega": "", "garantia": "", "site": "", "observacoes": "" },
  "aprendizado": { "periodo": "semanal" },
  "aparencia": { "tema": "claro", "cor_destaque": "#FACC15", "nome_exibido": "Loja Exemplo" }
}
```

- `aparencia` (opcional, chat do lead — seção 11): `tema` = `claro` (padrão) | `escuro` | `marinho`; `cor_destaque` opcional `#RRGGBB`; `nome_exibido` opcional (texto até 80; vazio = `nome`). Outra chave, tema fora da lista ou cor fora do formato → 422. **Contraste AA:** a letra sobre a cor de destaque é a de maior contraste entre `#1a1206` e `#ffffff`; se mesmo essa ficar abaixo de **4,5:1** (WCAG 2.x), o `PUT /api/gestor/config` dá 422 com mensagem que contém `contraste` e `4,5` e nada muda.

- `info` (opcional, **base de conhecimento** — seção 4a): textos livres, todos opcionais. `horario_atendimento` vazio = gerado dos `horarios`. Cada valor é texto (até 2000 caracteres); outra chave → 422.
- `aprendizado.periodo`: `diario` | `semanal` (padrão) | `desligado` — geração automática das propostas para a base (seção 13a). Outro valor → 422. do colaborador no painel da equipe e no `/entrar` do Telegram. Únicos.
- `preco` é opcional; o agente só fala preço que estiver aqui. **Promoção (1.6.8, opcional):** `preco_promocao` (texto, ex. `R$ 670`), `promocao` (nome curto, ex. `Promoção Black`) e `promocao_ate` (`AAAA-MM-DD`, inclusive; vazio = sem prazo). Enquanto vale (`preco_promocao` preenchido e hoje ≤ `promocao_ate` pelo relógio do servidor), o agente e o cérebro dizem `R$ 670 (Promoção Black até 30/11)`; depois volta o `preco` normal. Texto até 200; data fora do formato → 422.
- `cerebro.tipo`: `regras` (padrão) | `anthropic` | `openrouter` | `openai` | `ollama` | `claude_cli` | `codex_cli` (seção 14).
- `cerebro_curadoria` (1.6.8, opcional): `{tipo, modelo, esforco, url}` com os mesmos tipos e a mesma validação do `cerebro` (chave no JSON → 422). Ausente, `{}` ou `tipo` vazio = usa o `cerebro` principal. Usado **só** na geração de propostas do Aprendizado (seção 13a); sugestões, respostas ao lead e resumos ficam no `cerebro`.
- Todos os textos de "nome" podem ter acento; telefones são só dígitos.
- `prazos.assumir_imediato_min` (padrão 1) e `prazos.assumir_extremo_min` (padrão 10), opcionais: faixas do tempo para assumir no `/api/gestor/hoje` (seção 13). Inteiros ≥ 1 e `assumir_imediato_min < assumir_extremo_min` (com os padrões no lugar do que faltar); senão o `PUT /api/gestor/config` dá 422.

## 3. Autenticação

- **[G] gestor:** header `X-Token` = `token_gestor`. Errado/ausente → 401.
- **[E] equipe:** header `X-Codigo` = `codigo` de um colaborador → age como esse colaborador. Errado → 401. [G] também passa nas rotas [E] informando `"colaborador": "<id>"` no corpo quando precisa.
- Comparação em tempo constante (`hmac.compare_digest`). **Limite de tentativas:** 5 `X-Token`/`X-Codigo` errados por IP em 1 minuto → as próximas **erradas** recebem **429** `{"erro": "Muitas tentativas, aguarde."}` até a janela passar. Uma credencial **certa sempre passa** (o bloqueio conta e barra só falhas; a equipe inteira atrás do mesmo proxy não fica trancada por um chute).
- **IP do cliente:** o da conexão. Se a conexão vem de um **proxy confiável** — `ATENDE_PROXY_CONFIAVEL`, lista de CIDRs separada por vírgula, padrão `127.0.0.1/32,::1/128,172.16.0.0/12,10.0.0.0/8,192.168.0.0/16` (Caddy/Nginx no host chegando ao container pelo gateway da bridge do Docker) — vale o `X-Forwarded-For`: o primeiro IP não confiável lido da direita para a esquerda (o proxy acrescenta o cliente no fim). Vazio = nunca usa o `X-Forwarded-For`. Esse IP vale para todos os limites por IP (seções 3 e 4).
- **Lead:** página `/meu/<token_lead>` e rotas `/api/meu/<token_lead>...`; token aleatório ≥ 16 caracteres gerado na criação do lead. Token inexistente → 404. O token só é entregue ao próprio lead: ao lead do WhatsApp pelo próprio WhatsApp (link `Acompanhe aqui`), ao lead do chat web na resposta da sua sessão.
- **Sessão do chat web:** token aleatório ≥ 24 caracteres (`sessao`), criado na primeira mensagem web; é a identidade do lead web.
- Públicas: `/`, `/widget.js`, `/equipe`, `/gestor` (páginas; os dados vêm de rotas protegidas), `/web/fontes/*` (Sora e Inter, OFL), `/api/saude`, `GET /api/aparencia`, `POST /api/mensagens` (canal `web`), `GET /api/web/<sessao>`, `/ligar/<token_chamado>`.
- Webhooks com segredo próprio (seções 15–16).

## 4. Lead e conversa (`POST /api/mensagens`)

Corpo: `{"telefone": "...", "texto": "...", "nome": "opcional", "canal": "web|whatsapp", "sessao": "opcional"}`. Telefone normalizado: só dígitos; com 10 ou 11 dígitos ganha `55` na frente; resultado com menos de 12 ou mais de 13 dígitos → 422. `nome` (opcional) só é gravado se passar na mesma validação do nome da qualificação (1–4 palavras só de letras, 2–40 caracteres, sem dígitos, sem começar por negação/verbo/saudação); inválido é ignorado e o agente pergunta o nome depois. Resposta: `{"lead": {id, token, status, nota}, "respostas": ["..."]}` (lista de textos que o agente manda ao lead, na ordem; pode ser vazia).

- **`canal: "web"`** (padrão, público): sem `sessao` → cria **sempre um lead web novo** (o `telefone` é obrigatório, mas é só dado de contato, não identidade) e a resposta traz `"sessao": "<token ≥ 24>"`. Com `sessao` → a mensagem vai ao lead dessa sessão (`telefone` ignorado); sessão inexistente → 404. Um lead web **nunca** se mistura com o lead do WhatsApp de mesmo número. Mensagens ao lead web (avisos, respostas do colaborador) não vão por WhatsApp: ficam na caixa de saída com `status: "web"` e aparecem no chat por `GET /api/web/<sessao>` → `{"lead": {...}, "colaborador", "mensagens": [{de, texto, em, tipo}]}` (últimas 50; `tipo` = `aviso` nos avisos automáticos ao lead — `<nome> vai te atender agora.`, `Combinado! ...` —, senão igual a `de`). O chat web mostra as mensagens `humano` e os `aviso`.
- **Limites do chat web** (por IP da seção 3, em memória): no máximo **5 leads web novos por IP em 10 min** e **30 leads web novos no total por minuto** → **429** (a conversa de uma `sessao` existente continua). Chamados abertos pelo chat web ou por `POST /api/meu/<token>/falar`: além de **1 chamado aberto por lead** (regra 4), no máximo **3 por hora por IP** → **429** e nada é gravado.
- **`canal: "whatsapp"`** por esta rota é a **simulação** do WhatsApp (testes/demonstração) e exige **[G]** (sem token → 401). O WhatsApp real chega pelo webhook (seção 15). Identidade = telefone.

Lead criado no primeiro contato com `status: "novo"`, `nota: "frio"`. O texto é **normalizado** (minúsculas, sem acento, sem pontuação) para decidir. Ordem de decisão:

1. **Parar** — texto igual a `parar`, `sair` ou `pare`: lead `nao_contatar = true`; resposta contém `não vai mais receber`. Nenhuma mensagem automática (retorno, aviso de prazo) vai mais para ele. Mensagens novas dele continuam sendo recebidas (e tiram o `nao_contatar`, com resposta normal a partir daí).
2. **Apagar** — texto igual a `apagar meus dados`: anonimiza o lead (nome → `apagado`, telefone → `apagado-<id>`, mensagens e notas apagadas, chamados mantidos só com resultado e valores); resposta contém `apagados`. Chamado **aberto** do lead é fechado com `resultado: "apagado"`: oferta, alerta, linha do grupo e cartão do atendimento são editados para `🗑️ #<id> lead pediu para apagar os dados` (sem botões), o dono (se havia) recebe esse texto no privado e volta a livre como no fechamento (seção 6), e o lead volta ao status anterior a `em_atendimento`. Envios ainda pendentes na caixa de saída do Telegram e do WhatsApp com dados dele são cancelados, e retornos agendados dele, apagados. As mensagens já entregues no privado do dono com dados dele — `💬 <nome>: <texto>`, `📅 Retorno: ...` e `Ainda com <nome>?`, de qualquer chamado do lead, inclusive fechado — também são editadas para `🗑️ #<id> lead pediu para apagar os dados`.
3. **Em atendimento humano** — se o lead tem chamado `atendendo`: o agente **não responde** (`respostas: []`); a mensagem vai ao colaborador dono, no privado do Telegram, como `💬 <nome ou telefone>: <texto>` (seção 16).
4. **Chamado aguardando** (`aguardando` ou `alerta`): o agente não abre outro chamado nem inicia qualificação, mas **continua tirando dúvidas** enquanto ninguém assume: pergunta de horário, FAQ, informações do negócio, preço de produto cadastrado e, com cérebro LLM, a dúvida pela base (mensagens com 3+ palavras). Sem resposta → texto que contém `já avisei`. A mensagem entra no histórico do chamado.
4a. **Pergunta de horário / disponibilidade** (seção 4a) — antes das regras 5–7, porque `que hora tem atendimento humano?` contém `humano` e não é pedido de humano.
5. **Pediu humano** — contém `atendente`, `humano`, `falar com alguem`, `falar com uma pessoa`, `vendedor`, `me liga`, `me ligue` ou `ligacao`: abre chamado `motivo: "pediu_humano"`. Resposta contém `vou chamar`.
6. **Chance de venda** — contém `quero comprar`, `quero contratar`, `como faco para comprar`, `como faco para contratar`, `quero fechar`, `fechar negocio`, `fechar o pedido`, `fechar a compra`, `quanto custa`, `qual o valor`, `qual o preco`, `forma de pagamento`, `parcela`, `orcamento`: o lead fica `nota: "quente"`. Se casar um produto (seção 5) com `preco`, a resposta inclui o preço (`<nome>: <preco>`). Abre chamado `motivo: "venda"`. Resposta contém `vou chamar`.
7. **Necessidade** — contém, como **palavra ou expressão inteira** (aceita plural com `s`), `reclamacao`, `reclamar`, `problema`, `nao funciona`, `defeito`, `cancelar`, `reembolso`, `absurdo`, `pessimo`, `procon`: abre chamado `motivo: "precisa"`. Resposta contém `vou chamar`. **Negação simples não dispara:** o termo logo depois de `sem`, `nenhum`/`nenhuma`, `nao tem`, `nao ha`, `nao e` (ex.: `sem problema`, `nenhum problema`, `não tem problema`).
7a. **Informações do negócio** (seção 4a): endereço, pagamento, entrega, garantia/trocas, site — só se o campo de `info` estiver preenchido.
8. **Qualificação em andamento** consome a mensagem (abaixo).
9. **FAQ** — palavras significativas (≥ 3 letras, fora de artigos/preposições/pronomes comuns) de alguma pergunta: se ≥ 60 % aparecem no texto, responde **exatamente** a `resposta` (uma mensagem). Mais de um casa → maior %; empate → primeiro.
10. **Interesse em produto** — casa algum produto (seção 5): lead `nota: "morno"` (se não for `quente`), `interesse = <id do produto>`; se o lead ainda não tem nome, inicia a qualificação; senão responde texto que contém o nome do produto e pergunta `Quer que eu chame alguém para te atender?`; um `sim`/`quero`/`pode` na mensagem seguinte abre chamado `motivo: "venda"`.
11. **Primeiro contato** sem nada casado → saudação com o nome do negócio e inicia a qualificação.
12. **Não sei** — nem as regras nem o cérebro respondem: a resposta é `Essa eu não sei responder com certeza. Quer que eu chame alguém da equipe?` (não diz mais `não entendi`). Um `sim`/`quero`/`pode` (palavras de sim da regra 10) na mensagem seguinte abre chamado `motivo: "precisa"` (resposta contém `vou chamar`); `não` encerra (`qualquer dúvida`) sem chamado; outra coisa segue as regras. Na **segunda seguida** sem resposta, abre chamado `motivo: "precisa"` sozinho (resposta começa por `Essa eu não sei responder com certeza.` e contém `vou chamar`).

**Qualificação** (estado por lead, persistido): pergunta o **nome** (resposta contém `nome`) se o lead não tem nome. A resposta só vira nome se **parecer nome**: 1 a 4 palavras, só letras, espaço, apóstrofo e hífen, 2–40 caracteres, sem dígitos, e a primeira palavra fora de uma lista de negações/verbos/saudações comuns (`não`, `sim`, `quero`, `tenho`, `oi`, `olá`, `bom`, `boa`, ...); senão pergunta de novo `Pode me dizer só o seu nome?` (prefixos `meu nome é`, `me chamo`, `sou` são tirados antes). O `pushName` só é oferecido (`Posso te chamar de ...?`) se parecer nome. → depois **o que procura** (lista os produtos numerados `1 - <nome>`, e `0 - Outro assunto`) → depois **para quando** (`1 - Hoje / esta semana`, `2 - Este mês`, `3 - Só pesquisando`). Ao fim: urgência 1 → `quente` e abre chamado `venda`; 2 → `morno`, resposta pergunta se quer falar com alguém (como na regra 10); 3 → `frio`, resposta contém `qualquer dúvida` e não abre chamado. Número inválido repete as opções. As regras 1–7 valem também no meio da qualificação.

- Abrir chamado não depende de qualificação completa: os dados que houver vão no aviso.
- Se o lead mandou `nome` no corpo e ainda não tem nome, usa esse.
- O agente **nunca** inventa preço, prazo de entrega ou condição: só o que está em `negocio.json`.
- **Status do lead:** `novo` → `em_atendimento` (chamado assumido) → `negociando` | `retornar` | `ganho` | `perdido` | `invalido` (pelo fechamento, seção 9). Lead com chamado aberto e ainda não assumido continua no status anterior.

### 4a. Respostas automáticas da base de conhecimento (`info`)

- **Horário / disponibilidade (regra 4a)** — o texto fala de horário (`horario`, `que hora(s)`, `ate que horas`, `expediente`, `funcionamento`, `abre`, `fecha`, `aberto`) **ou** de disponibilidade (`tem alguem`, `alguem ai`, `estao atendendo`, `tem atendimento`, `esta atendendo`) **e não** traz verbo de pedido (`quero`, `preciso`, `falar com`, `me liga`, `me ligue`, `ligacao`, `chama`, `chamar`). Resposta (uma mensagem): `info.horario_atendimento` se preenchido; senão, se um item do FAQ casar (regra 9) → exatamente a `resposta` dele; senão o texto gerado dos `horarios` (`Nosso atendimento: seg a sex 08:00–18:00; sáb 09:00–13:00.`). Com `info` ou gerado (não no FAQ, que sai exato) acrescenta o agora: `Agora estamos atendendo.` ou `Agora estamos fora do horário; voltamos DD/MM às HH:MM.`. Não abre chamado.
- **Pagamento** — a regra 6 continua (abre chamado de venda); se `info.pagamento` estiver preenchido, a resposta ganha o prefixo `Formas de pagamento: <pagamento>. ` (como o preço). Pergunta de pagamento sem gatilho de venda (`pix`, `cartao`, `boleto`, `pagamento`, `pagar`, `parcelar`, `parcelamento`, `parcela(s)`, `aceita(m)`, `como pago`) → responde `Formas de pagamento: <pagamento>` na regra 7a.
- **Regra 7a** (só campo preenchido): endereço (`endereco`, `onde fica`, `onde voces ficam`, `localizacao`, `como chego`) → `Endereço: <endereco>`; entrega (`entrega`, `entregam`, `frete`, `envio`, `enviam`, `retirada`, `delivery`) → `Entrega: <entrega>`; garantia/trocas (`garantia`, `troca`, `trocas`, `trocar`, `devolucao`, `devolver`) → `Garantia e trocas: <garantia>`; site (`site`, `website`) → `Site: <site>`. Vale também no meio da qualificação (mantém a etapa, como o FAQ). Campo vazio → não responde nada daquilo e a mensagem segue as regras seguintes (nunca inventa).
- `info.observacoes` não gera resposta automática: só entra no contexto do cérebro (seção 14).
- **Testar** `POST /api/gestor/testar {"texto": "..."}` [G] → roda a conversa (regras 1–12 e o cérebro, se ligado) num **lead fictício** já com nome e uma mensagem anterior, e desfaz tudo (banco, caixa de saída, Telegram): nada é gravado. Resposta `{"respostas": [...], "chamado": "<motivo>"|null}`. Texto vazio → 422.

## 5. Produtos

Preço dito pelo agente = o **preço vigente** (seção 2: promocional dentro da validade, senão `preco`). Um produto casa se alguma de suas `palavras` (normalizada) aparece no texto normalizado, ou se o nome normalizado aparece. Mais de um → o primeiro na ordem do `negocio.json`.

## 6. Equipe e status

- Status do colaborador: `livre` | `ocupado` | `fora` | `atendendo`. Começa `fora`.
- `livre_desde`: momento em que ficou `livre` pela última vez. **Ordem de vez** = livres ordenados por `livre_desde` crescente (empate: ordem do `negocio.json`).
- O colaborador muda para `livre`, `ocupado` ou `fora` pelo painel, pelo Telegram (botões ou `/livre`, `/ocupado`, `/fora`) ou o gestor muda por ele. `atendendo` só vem de assumir chamado.
- Colaborador com 1+ chamado `atendendo` fica `atendendo`. Ao fechar o último, volta a `livre` com `livre_desde = agora` (fim da fila).
- Mudar para `fora` com chamados `atendendo` → 409.

## 7. Chamados e roteamento

Chamado: `{id, lead_id, motivo: pediu_humano|venda|precisa, prioridade: quente|normal, status: aguardando|alerta|atendendo|fechado, ofertado_a, recusaram: [], dono, aberto_em, assumido_em, fechado_em, resultado}`. Prioridade `quente` se `motivo = venda` ou lead `quente`; senão `normal`.

- **Abrir:** no horário de atendimento (seção 10). Grava o chamado `aguardando` e:
  1. manda ao **grupo** uma linha curta: começa com `🔥` (quente) ou `🙋` (normal), contém `#<id>`, o primeiro nome do lead (ou `lead`, se não houver nome ou se a primeira palavra tiver dígito ou nenhuma letra — vale para todo texto do grupo e do painel), o motivo legível (`pediu humano` / `chance de venda` / `precisa de atenção`) e, se ofertado, `→ <nome do colaborador>`. **Sem telefone** no grupo.
  2. **oferta** ao primeiro da ordem de vez que não esteja em `recusaram`: mensagem **privada** (seção 16) com `#<id>`, nome, telefone formatado `+55 (41) 99999-0001`, nota, motivo, interesse (nome do produto), resumo (seção 14) e as últimas 5 mensagens do lead; botões **✅ Assumir**, **↪️ Passar**, **📞 Ligar**, **💬 WhatsApp**. `ofertado_a = <id>`, `ofertado_em = agora`.
  3. ninguém livre → nenhuma oferta; vai direto ao **alerta** (abaixo).
- **Oferta vencida:** passados `prazos.oferta_min` desde `ofertado_em` sem assumir → conta como recusa e oferece ao próximo (mesma mensagem). O aviso antigo é editado para `⌛ #<id> passou para o próximo` (sem botões).
- **Passar:** o ofertado toca **↪️ Passar** → recusa imediata, vai ao próximo.
- **Alerta 🚨:** chamado ainda não assumido depois de `alerta_quente_min` (quente) ou `alerta_normal_min` (normal) contados de `aberto_em`, **ou** sem ninguém livre que ainda não recusou → status `alerta` e mensagem ao **grupo** começando com `🚨`, contendo `#<id>`, nome, motivo, nota, interesse e há quantos minutos espera, com botão **✅ Assumir** (qualquer colaborador cadastrado). Telefone **não** vai no grupo. Um alerta por chamado; enquanto em `alerta` continua oferecendo a quem ficar livre.
- **Assumir** (botão no privado, botão do alerta, painel da equipe ou gestor transferindo): pelo colaborador ([E] em `/api/equipe/chamados/{id}/assumir` ou botão `as:` no Telegram) só vale para **o chamado ofertado a ele** ou **em `alerta`**; senão **403** (no Telegram, a resposta `Este chamado não foi oferecido a você`). O gestor passa um chamado a qualquer um por `transferir` (seção 13); [G] na rota da equipe com `"colaborador"` também não tem essa restrição. Atômico — só o primeiro vence; os outros recebem 409 na API e no Telegram a resposta `já foi assumido por <nome>`. Ao assumir: `status: atendendo`, `dono`, `assumido_em`; colaborador `atendendo`; lead `em_atendimento`; mensagens do grupo do chamado (linha e alerta) editadas para `✅ <nome> assumiu #<id>` (sem botões); o dono recebe no privado o **cartão do atendimento** com os botões de fechamento (seção 9); o lead recebe `<nome do colaborador> vai te atender agora.` Colaborador `fora` não pode assumir (409); `ocupado` pode (vira `atendendo`).
- **Lead que volta:** se o lead teve chamado fechado nos últimos 30 dias com dono, a oferta do novo chamado vai **primeiro** a esse dono se ele estiver `livre`; senão segue a ordem de vez.
- **Mensagens do dono ao lead:** no privado, responder (reply) ao cartão, a uma mensagem `💬` do lead ou a uma `💡 Sugestão` → o texto vai ao lead (WhatsApp/caixa de saída `tipo: "humano"`). Também `POST /api/equipe/chamados/{id}/responder {texto, sugestao_id?}` [E].

### 7a. Sugestão de resposta e registro de aprendizado

- Mensagem do lead num chamado `atendendo` (regra 3) cria uma **sugestão** (tabela `sugestoes`) para o dono, gerada **fora do lock e de forma assíncrona** (um trabalhador em segundo plano; a resposta ao lead/webhook não espera). Contexto: a base (seção 14), as últimas 10 mensagens e os dados do lead. Sem cérebro LLM (ou ele falhou): sugestão por regras = a resposta da seção 4a ou do FAQ que casar com a mensagem; senão nenhuma. Sugestão anterior ainda não usada do mesmo chamado vira `substituida`.
- Telegram (privado do dono): depois do `💬 <nome>: <texto>`, `💡 Sugestão: <texto>` com botões **✅ Enviar** (`sg:<id>:ok`) e **✏️ Editar** (`sg:<id>:ed`). `ok` manda o texto ao lead como resposta do dono e edita a mensagem para `✅ Enviada: <texto>`; `ed` → o bot manda `Mande o texto editado respondendo a esta mensagem.` e o próximo reply a ela (ou ao `💡`) vira a resposta, ligado à sugestão. Com conflito (1.6.8): o texto ganha `\n\n⚠️ <conflito>` e uma linha com o botão **📚 Atualizar a base** (`sb:<id>`, mesmo efeito do `POST …/base`; responde `Enviado ao gestor ✓`); depois de enviada ou ignorada, a mensagem editada mantém o aviso e o botão `sb:` até a proposta ser criada. Sugestão já usada/substituída → `Essa sugestão já foi usada ou substituída.` O reply livre ao `💬` continua valendo.
- **A sugestão é a fala do vendedor (1.6.8).** Com cérebro LLM, a instrução própria da sugestão (substitui a instrução geral; não usa "Se a base não responder, diga que vai chamar alguém da equipe") pede a próxima mensagem do vendedor, **em primeira pessoa**, com a **ordem de verdade**: (a) o que o vendedor já afirmou nesta conversa (preço, promoção, prazo, condição) vale sobre a base, e entre afirmações diferentes vale a **última**; (b) a base. Nunca mencionar base, sistema, IA, "o vendedor", "a equipe vai confirmar" por divergência interna, nem pedir desculpa por inconsistência; não inventar o que não está na conversa nem na base (se faltar, perguntar ao cliente ou dizer que vai verificar). Saída JSON `{"resposta": "<texto pronto>", "conflito": "<1 frase interna para o vendedor sobre divergência base × conversa, ou vazio>"}`; no tipo `anthropic` vai também `output_config.format = {type: json_schema, schema}` (structured outputs). Leitura tolerante: JSON puro, dentro de cerca ```` ```json ````, ou texto livre (= resposta, conflito vazio). `limpar_md` na resposta. O `conflito` fica na coluna `sugestoes.conflito`.
- Ficha da equipe (`GET /api/equipe/leads/{id}`) traz `sugestao: {id, texto, em, conflito, proposta_id}|null` (a última `pronta` do chamado aberto; `conflito` = `""` se não houver); o painel pré-preenche a caixa de resposta com ela.
- **Atualizar a base:** `POST /api/equipe/sugestoes/{id}/base` [E] (o dono do chamado, ou o gestor) cria **uma** proposta (seção 13a, `origem: vendedor`) por sugestão e devolve `{"ok": true, "proposta": <id>}` (repetir devolve a mesma, com `ja_enviada: true`). O conflito **nunca** vira texto da base: se as mensagens do vendedor têm `R$ …` e há produto (citado no conflito ou o `interesse` do lead) → proposta `preco` (`preco_novo` = o último R$ que o vendedor escreveu, `promocao` = `Promoção <Nome>` se ele citou); senão `info`/`observacoes` com a última mensagem do vendedor ao cliente como rascunho. `justificativa` = conflito + trecho da conversa. Sugestão sem conflito → 422; chamado de outro → 409.
- **Aprendizado** (tabela `aprendizado`): cada resposta humana a mensagens do lead (as do lead desde a última resposta humana) grava `{em, colaborador, lead_id, chamado_id, msg_lead, sugestao, enviado, origem, distancia}`: `origem` = `sugestao_ok` (com `sugestao_id` e texto igual), `sugestao_editada` (com `sugestao_id` e texto diferente) ou `livre` (sem `sugestao_id`; `sugestao` = a última sugestão pronta do chamado, se havia — "ignorada"); `distancia` = **similaridade** 0–1 (`difflib.SequenceMatcher.ratio`) entre sugestão e enviado, `null` sem sugestão. Resposta sem mensagem do lead pendente não grava. `apagar meus dados` apaga sugestões e aprendizado do lead.
- **Ligar:** `GET /ligar/<token_chamado>` → página HTML mínima que redireciona para `tel:+<telefone>` (meta refresh + link visível). O botão 📞 do Telegram é um botão de URL para `{url_publica}/ligar/<token_chamado>`. O telefone também vai em texto na mensagem. `token_chamado` aleatório ≥ 16; inexistente → 404.
- **WhatsApp:** botão de URL `https://wa.me/<telefone>`.

## 8. Painel fixo no grupo

- Uma mensagem no grupo com o título `EQUIPE AGORA`, a hora (`HH:MM`), uma linha por colaborador (`🟢 <nome> livre há N min`, a primeira da ordem de vez com `(próxima da vez)`; `🟡 <nome> atendendo <primeiro nome do lead> · N min`; `🔴 <nome> ocupado`; `⚫ <nome> fora`) e a seção `FILA` com os chamados `aguardando`/`alerta` (`🔥`/`🙋` `<primeiro nome> · esperando N min`, e `⚠️ sem dono` se em alerta).
- Criada na primeira mudança (status, chamado). Depois é **editada** (`editMessageText`) em cada mudança, nunca reenviada. Só se o Telegram responder **400** dizendo que a mensagem não existe ou não pode ser editada (`message to edit not found`, `message can't be edited`) envia uma nova e guarda o novo `message_id`. Erro transitório — **429** (espera o `parameters.retry_after`), 5xx, timeout/conexão — tenta **editar** de novo mais tarde (backoff da seção 15), sem `sendMessage`; outro erro 4xx desiste daquela edição (a próxima mudança edita de novo). Tenta fixar (`pinChatMessage`) ao criar; falha ao fixar é ignorada.
- `/status` no grupo da equipe (`TELEGRAM_GRUPO_ID`) ou no privado → o bot manda o mesmo texto (mensagem nova). Em outros grupos, ignorado.
- `GET /api/painel` [G] ou [E] → `{"equipe": [{id, nome, status, livre_desde, minutos, proximo}], "fila": [{id, lead, prioridade, status, minutos, ofertado_a}]}`.

## 9. Fechamento

`POST /api/equipe/chamados/{id}/fechar` [E] (só o dono; [G] pode fechar qualquer) com:
```json
{"resultado": "vendeu|retornar|negociando|sem_interesse|invalido",
 "valor": 1200.0, "produto": "plano-anual", "retornar_em": "AAAA-MM-DDTHH:MM",
 "motivo": "preco|ja_comprou|curioso|outro|numero_errado|spam|nao_e_lead", "nota": "texto livre"}
```
- Obrigatórios por resultado: `vendeu` → `valor` (≥ 0); `retornar` → `retornar_em` (no futuro); `sem_interesse` e `invalido` → `motivo` (valores da lista acima, `numero_errado|spam|nao_e_lead` só para `invalido`, os outros só para `sem_interesse`). Faltou/errado → 422. Não é dono → 403. Já fechado → 409.
- Efeito: chamado `fechado` com `resultado`; lead `status`: vendeu → `ganho`, retornar → `retornar`, negociando → `negociando`, sem_interesse → `perdido`, invalido → `invalido`. Colaborador volta a `livre` (seção 6) se não tiver outro chamado. Grava no **histórico do lead** um evento `{em, colaborador, resultado, valor, produto, motivo, nota, minutos_ate_assumir, minutos_atendimento}`. `minutos_ate_assumir` conta do **início do prazo** do chamado (a abertura do expediente, se ele chegou fora do horário — seção 10; senão `aberto_em`) até `assumido_em`; o `tempo_medio_assumir_min` do `/api/gestor/hoje` usa a mesma conta.
- **Retorno:** `retornar` agenda; em `retornar_em` (tarefa de tempo) o mesmo colaborador recebe no privado `📅 Retorno: <nome> +55 (...)` com os botões Ligar/WhatsApp e um botão **✅ Assumir** que reabre um chamado `motivo: "venda"` já assumido por ele.
- **Pelo Telegram** (cartão do atendimento): botões `✅ Vendeu`, `📅 Retornar`, `🤔 Negociando`, `❌ Sem interesse`, `🚫 Inválido`, `↩️ Devolver ao bot`. Cada um conduz as perguntas pelo próprio bot no privado (botões para motivo e data — `Amanhã 09:00`, `Em 3 dias 09:00`, `Semana que vem 09:00` —, texto para valor e nota; a nota é opcional, botão `Pular`). Ao final chama o mesmo fechamento.
- **Áudio como nota:** mensagem de voz no privado durante o fechamento → se `WHISPER_CMD` estiver definida (comando local que recebe o caminho do arquivo e imprime o texto), transcreve e usa como nota; senão guarda `"[áudio]"` como nota. Nunca chama API externa para isso.
- **Devolver ao bot:** `POST /api/equipe/chamados/{id}/devolver` [E] → chamado `fechado` com `resultado: "devolvido"`, lead volta ao agente (status anterior a `em_atendimento`), colaborador livre como no fechamento.
- **Mensagem ao lead após fechar:** só em `retornar`: `Combinado! Vamos te procurar em DD/MM às HH:MM.`

## 10. Horário, fora do horário e lembretes

- Horário de atendimento = `horarios` do `negocio.json` (dias `seg ter qua qui sex sab dom`, janelas `[ini, fim)`).
- Fora do horário, um chamado é aberto em `aguardando` mas **não** é ofertado nem gera alerta; o lead recebe texto contendo `fora do horário` e o próximo início (`DD/MM às HH:MM`). Na abertura do expediente (tarefa de tempo), os chamados aguardando são ofertados na ordem em que foram abertos, e os prazos de alerta contam a partir da abertura do expediente.
- **Lembrete de atendimento parado:** chamado `atendendo` sem mensagem nova (do lead ou do dono) há `lembrete_min` → o dono recebe `Ainda com <nome>?` com botões **Sim, continuo** (zera a contagem) e **Terminei** (abre o fechamento). Um lembrete por período parado.
- **Fim do expediente:** no fim da última janela do dia (tarefa de tempo), cada dono com chamado `atendendo` recebe `Fim do expediente: feche seus atendimentos`, e o grupo recebe a lista dos ainda abertos.

## 11. Interface do lead

- `GET /` → chat web (a mesma conversa da seção 4, telefone e nome pedidos na tela). Caixa de escrever fixa embaixo (`100dvh`), mensagens ancoradas junto dela; o "Olá" automático que cria o lead não aparece como se o lead tivesse escrito; ao voltar à página, a conversa inteira é mostrada.
- **Aparência** `GET /api/aparencia` (pública) → **só** `{tema, cor_destaque, cor_destaque_texto, nome_exibido}` (padrões: `claro`, `null`, `null`, `nome` do negócio; `cor_destaque_texto` = a letra escolhida pela regra de contraste da seção 2). O chat aplica o tema (`data-tema` no `<html>`) e, se houver, a cor de destaque (botões e bolha do lead) e o nome exibido no cabeçalho.
- **Temas** (um único `web/style.css`, só variáveis CSS mudam): `claro` (padrão, "Balcão"), `escuro` (Plantão INEMA: fundo `#0c0c10`, amarelo `#FACC15` só em ação) e `marinho`. Ícones de traço em SVG (sem emoji como ícone), fontes Sora/Inter locais em `web/fontes/` (OFL) com a pilha do sistema como reserva, nenhuma CDN. Texto com contraste AA nos três, foco visível, alvos de toque ≥ 44 px no celular, `prefers-reduced-motion` respeitado.
- `GET /widget.js` → script que coloca uma bolha de chat em qualquer site e abre o chat num iframe para `{url_publica}/?widget=1`; leva a aparência embutida (cor de destaque na bolha, fundo do tema na caixa).
- `GET /meu/<token_lead>` → página "meu atendimento": nome do negócio, status do lead em texto (`Recebemos sua mensagem`, `Alguém da equipe vai falar com você`, `<nome> está te atendendo`, `Retorno marcado para DD/MM às HH:MM`, ...), nome do colaborador se houver, botão **Quero falar agora** e botão **Apagar meus dados**.
- `GET /api/meu/<token_lead>` → **só** `{nome, status, colaborador, retornar_em}` (nunca o texto das mensagens). `POST /api/meu/<token_lead>/falar` → abre chamado `pediu_humano` (mesmas regras da seção 4 regra 4/5). `POST /api/meu/<token_lead>/apagar` com `{"confirmar": true}` → igual à regra 2; sem a confirmação → 422 e nada muda.
- O chat web guarda a `sessao` no `localStorage` do navegador e manda em cada mensagem; as respostas da equipe chegam por `GET /api/web/<sessao>`.
- O link `/meu/<token>` **não** é enviado por padrão (o lead já está na conversa). Com `"link_acompanhamento": true` no `negocio.json`, vai ao lead do **WhatsApp** quando abre chamado (`Acompanhe aqui: {url_publica}/meu/<token>`); nunca no chat do site.
- Botões de contato: `📞 Ligar (telefone)` (ligação comum pela operadora, via `/ligar/<token>` → `tel:`) e `💬 WhatsApp (conversa ou chamada)` (`wa.me`; a chamada de WhatsApp é feita tocando no ícone dentro da conversa). A oferta traz essa explicação em duas linhas.

## 12. Painel da equipe (`/equipe`, rotas [E])

- `GET /api/equipe/eu` → `{id, nome, status, chamados: [abertos dele], retornos_hoje: [...]}`.
- `POST /api/equipe/status {"status": "livre|ocupado|fora"}`.
- `POST /api/equipe/chamados/{id}/assumir` · `/passar` · `/responder` · `/fechar` · `/devolver`.
- `POST /api/equipe/sugestoes/{id}/base` → `{ok, proposta}` (1.6.8, seção 7a).
- `GET /api/equipe/leads/{id}` → ficha: lead, mensagens, chamados, histórico. Colaborador só vê leads de chamados ofertados a ele, dele, ou em alerta; senão 403.
- `GET /api/equipe/leads/{id}` traz **todas** as mensagens do lead, inclusive as que chegaram depois do fechamento/devolução, e o `lead` da ficha leva também `minutos_conversa`, `dias_contato` e `dia_anterior` (abaixo). Aberta por um colaborador ([E]), marca como vistas por ele as mensagens do lead até ali (tabela `vistos(colaborador, lead_id, ate)`, `ate` = id da última mensagem): as `novas` dele para esse lead zeram. O gestor abrindo a ficha não marca nada.
- `GET /api/equipe/contatos[?status=]` → **meus contatos**: lista dos leads que esse colaborador já atendeu — foi dono de algum chamado do lead, está no histórico de fechamento dele, ou tem chamado do lead ofertado a ele agora (`aguardando`/`alerta`). Leads anonimizados (apagados) não aparecem. Cada item: `{id, nome, telefone, status, nota, interesse, ultimo_contato, ultima_mensagem, novas, retornar_em, chamado_aberto, minutos_conversa, minutos_desde_contato, dias_contato, dia_anterior}`:
  - `ultima_mensagem`: texto da última mensagem **do lead**, até 120 caracteres (`null` se não houver).
  - `novas`: nº de mensagens do lead depois do último fechamento/devolução feito por **esse** colaborador e depois da última vez que ele abriu a ficha (o que for mais recente; contado por id da mensagem, não pelo minuto). 0 se ele nunca fechou/devolveu um chamado desse lead.
  - `retornar_em`: o retorno agendado mais recente do lead, se o status for `retornar`; senão `null`. `chamado_aberto`: id do chamado não fechado do lead ou `null`.
  - `minutos_conversa`: soma da duração dos atendimentos humanos do lead (`assumido_em` → `fechado_em`, ou até agora se aberto). `minutos_desde_contato`: minutos de `ultimo_contato` até agora. `dias_contato`: nº de dias distintos com mensagem do lead. `dia_anterior`: o dia (`AAAA-MM-DD`) mais recente com mensagem do lead **antes** do último dia de contato, ou `null`.
- **Ordem por nível** (vale também para `/api/gestor/leads`): `em_atendimento` → `retornar` (`retornar_em` mais próximo primeiro) → `negociando` → `novo` (com chamado aberto antes dos sem) → `ganho` → `perdido` → `invalido`; dentro do nível, `ultimo_contato` mais recente primeiro.
- Página `/equipe` (1.5): topo com o status em controle segmentado (o ativo marcado, `aria-pressed`) e o seletor de tema (claro/escuro/marinho, salvo por aparelho; sem escolha, vale `aparencia.tema`); faixa **Esperando por você** no topo com as ofertas e alertas (Assumir, Passar, ver conversa, Ligar, WhatsApp; tempo de espera e destaque `esperando demais` no alerta); no PC, três colunas — Meus contatos (busca e filtro por status) | conversa | ficha (dados, Ligar/WhatsApp, **Encerrar atendimento** com os campos de cada resultado, Devolver ao assistente). No celular a ficha é uma tela própria por cima, com **Voltar** e barra fixa embaixo: **Assumir** (lead esperando), ou sugestão + resposta (lead dele), ou aviso de só leitura; Encerrar atendimento abre uma folha por cima. Antes (1.4): entra com o código (guardado só na memória da aba), mostra status com botões, chamados abertos, retornos de hoje, **Meus contatos** (selo colorido do status, 🔥 se quente, última mensagem, selo `N nova(s)`, data do retorno, tempo de conversa `N min`/`N h M min`, `há N min/h/dias`, `também falou em DD/MM · N dias de contato`; filtro por status; clique abre a ficha), ficha com as mensagens, a **sugestão** (seção 7a) separada, com **Enviar** (manda como está), **Editar** (leva o texto para a caixa de resposta, ainda ligado à sugestão) e **Limpar** (tira o vínculo; a resposta conta como livre), e o formulário de fechamento. Tudo atualiza a cada 10 s. **1.6.8:** sugestão com `conflito` mostra acima dela um aviso discreto (ícone de alerta de traço + o texto do conflito) com o botão **Atualizar a base** (`POST /api/equipe/sugestoes/{id}/base`), que vira **Enviado ao gestor ✓** (desabilitado; também se a ficha já trouxer `proposta_id`).
- **Atualizar** (1.7.8): botão no topo (ícone de recarregar, tecla `R` com o foco fora de campos) relê `GET /api/equipe/eu`, os contatos e a ficha aberta sem sair; o texto da caixa de resposta fica; mostra `Atualizado às HH:MM`.

## 13. Painel do gestor (`/gestor`, rotas [G])

- `GET /api/gestor/ao-vivo` → igual a `/api/painel` + alertas abertos + `descartes`: as últimas 20 mensagens de entrada que não deu para atender (`{em, origem, motivo, ...}`, ex.: `remoteJid` `@lid` sem telefone). Webhook (Evolution ou Telegram) cujo tratamento desistiu — 503 depois das tentativas ou entrada que quebrou o tratamento — também entra em `descartes` (`origem` `evolution`/`telegram`), e a resposta ao webhook continua 200.
- **Quatro grupos (1.8.8)** em `GET /api/gestor/ao-vivo` e em `hoje.grupos`: `robo` (leads não apagados com `ultimo_contato` nas últimas `prazos.conversa_ativa_h` horas — padrão 24 —, sem chamado aberto e, se já tiveram chamado fechado, com mensagem do lead depois do último fechamento: `{lead_id, nome, telefone, nota, status, ultimo_contato, minutos_desde_contato, ultima_mensagem}`, mais recente primeiro), `espera` (chamados `aguardando`/`alerta`, mais antigos primeiro), `atendendo` (chamados `atendendo`, cada um com `sem_resposta_min` = minutos desde a 1ª mensagem do lead depois da última resposta da equipe e do assumir; `null` = respondido), `encerrados` (chamados fechados hoje, mais recentes primeiro), `sem_resposta` (os de `atendendo` com `sem_resposta_min` > `prazos.assumir_extremo_min`, pior primeiro) e `conversa_ativa_h`. Todos os itens trazem `lead_id`, nome e telefone (o gestor vê o telefone; `/api/painel` da equipe e o grupo do Telegram continuam sem). A `fila` do ao-vivo ganha `telefone`, `lead_nome`, `nota`. Depois do fechamento o agente volta a responder o lead normalmente (seção 6).
- `GET /api/gestor/hoje` → `{dia, agora, leads_novos, chamados_abertos, abertos_agora, assumidos, vendas, valor_vendido, tempo_medio_assumir_min, assumir, por_colaborador: [{id, nome, assumidos, vendas, valor, assumir}], chamados_abertos_agora: [...], leads_hoje: [...]}` do dia do relógio. `leads_novos` = leads criados hoje; `chamados_abertos` = chamados abertos hoje (qualquer status); `abertos_agora` = chamados `aguardando`/`alerta`/`atendendo` neste momento.
  - `assumir: {imediatos, medios, extremos, maior_min, media_min, imediato_min, extremo_min, tempos}` sobre os chamados assumidos hoje (`tempos` = a lista ordenada dos minutos de cada chamado, para a régua de pontos) (tempo contado como no fechamento, seção 9): **imediatos** ≤ `prazos.assumir_imediato_min` (padrão 1), **médios** acima disso e ≤ `prazos.assumir_extremo_min` (padrão 10), **extremos** > `assumir_extremo_min`; `maior_min` = o maior tempo do dia (0 se nenhum); `media_min` = `tempo_medio_assumir_min` (mantido por compatibilidade). O mesmo objeto por colaborador (pelo dono).
  - `chamados_abertos_agora`: os chamados `aguardando`/`alerta`/`atendendo` (como em `json_chamado`: `lead_nome`, `nota`, `status`, `dono`, `ofertado_a`, `minutos` desde a abertura), mais antigos primeiro.
  - `leads_hoje`: leads criados hoje **ou** com `ultimo_contato` hoje (não apagados), na ordem por nível da seção 12, mesmos campos de `/api/gestor/leads`.
- `GET /api/gestor/leads?status=&situacao=&contato=&colaborador=&de=&ate=` → lista na **ordem por nível** da seção 12 (os filtros continuam). Cada item tem `situacao` ∈ `atendendo | espera | robo | encerrado | parado` (1.8.8); `situacao=` filtra por ela; `contato=` filtra por `minutos_desde_contato`: `1h` (< 60), `24h` (< 1440), `1a7d` (1440 até < 10080), `mais7d` (≥ 10080). Cada item traz o lead, `colaborador`, `resultado`, `valor`, `chamado_status` do último chamado e `retornar_em`, `chamado_aberto`, `minutos_conversa`, `minutos_desde_contato`, `dias_contato`, `dia_anterior` (seção 12). `GET /api/gestor/leads/{id}` → ficha completa (o `lead` com os mesmos três campos de tempo da ficha da equipe).
- `POST /api/gestor/chamados/{id}/transferir {"colaborador": "<id>"}` → o chamado (aberto, assumido ou não) passa a ser do colaborador, como se ele tivesse assumido; o antigo dono volta a livre se ficar sem chamados. `POST /api/gestor/chamados/{id}/reabrir` → chamado fechado volta a `aguardando` (novo roteamento). `POST /api/gestor/equipe/{id}/status`.
- `GET /api/gestor/config` / `PUT /api/gestor/config` → lê e grava o `negocio.json` inteiro (valida: ids únicos, códigos únicos com **12+ caracteres**, horários `HH:MM`, prazos inteiros ≥ 1; inválido → 422 e nada muda). `token_gestor` nunca é devolvido no GET (vem `"***"`; `***` no PUT mantém o atual); um `token_gestor` novo precisa de 16+ caracteres e não pode ser `TROQUE-ESTE-TOKEN` nem o do `exemplos/negocio.json` (→ 422). O `negocio.json` é regravado com permissão `600`.
- `GET /api/gestor/exportar.csv` → CSV UTF-8 com cabeçalho `lead_id,nome,telefone,status,nota,interesse,colaborador,resultado,valor,criado_em,ultimo_contato`. Célula de texto que começa com `=`, `+`, `-`, `@`, tab ou CR ganha `'` na frente (sem injeção de fórmula na planilha).
- Página `/gestor` (1.8.8): **Ao vivo** = equipe em linha e quatro colunas — Robô atendendo · Esperando atendente · Em atendimento (cliente sem resposta acima do extremo em vermelho) · Encerradas hoje —, cada cartão com `#lead`, nome e telefone; alerta no topo de cliente sem resposta no atendimento (também no **Hoje**, que troca "Chamados abertos agora" pelos mesmos quatro grupos). **Leads**: filtros Situação e Último contato; colunas Situação, Último contato (há quanto tempo, cor por faixa) e Conversa; clicar no título da coluna ordena, 2º clique inverte, 3º volta à ordem por nível. Cadastros → Prazos ganha `conversa_ativa_h`.
- Página `/gestor` (1.5): abas na lateral (`role=tab`, setas do teclado), seletor de tema no topo. **Ao vivo** em colunas — equipe (livres e próximo da vez primeiro, status por pessoa) | em atendimento | fila (espera, esperando demais em destaque) — com transferir por seleção + botão e confirmação. **Hoje** abre com o alerta de quem espera mais que `assumir_extremo_min` (botão para a fila), a **régua de pontos** do tempo para assumir (um ponto por chamado nas faixas imediato/médio/extremo, linha da média), os números em linha e as tabelas; minutos sempre como `N min`, `N min S s` ou `H h M min`. **Leads** filtra ao mudar. **Cadastros** em formulário: Negócio, **Aparência** (tema, cor com prévia do contraste, nome exibido), Equipe (nome, telefone, código mascarado com mostrar e **gerar novo**), Produtos (nome, preço, palavras), Horários (janelas por dia) e Prazos (os seis números), salvos pelo mesmo `PUT /api/gestor/config`. Aba **Base consolidada** (1.6.8, seção 13b). **Atualizar** (1.7.8): botão no topo e nas abas Base de conhecimento, Base consolidada e Cadastros (tecla `R` com o foco fora de campos) relê `GET /api/gestor/config` e os dados da aba aberta e redesenha sem sair (a aba e os filtros ficam); com alteração não salva na aba, pergunta `Descartar alterações e atualizar?` numa faixa da própria página (sem `alert()`/`confirm()`); mostra `Atualizado às HH:MM`. Base de conhecimento ganha **Importar de link ou arquivo** (seção 13c); Base consolidada ganha **Perguntar à base**; Aprendizado ganha a seleção e **Incorporar selecionadas**. Antes (1.4): entra com o token; abas Ao vivo, Hoje (números, faixas do tempo para assumir, chamados abertos agora e leads de hoje), Leads (selo de status com as cores da equipe e os tempos da seção 12), **Base de conhecimento** (formulário: informações do negócio = `info`; FAQ com adicionar/editar/remover e várias formas da pergunta; caixa **Testar** = `POST /api/gestor/testar`; seletor do cérebro — tipo e os campos de cada um: `modelo`, `esforco` no anthropic, `url` no ollama/openai; a chave nunca aparece nem é editável pela web), **Aprendizado** (seção 13a), Cadastros (equipe, produtos, horários, prazos — com campos para os dois limites das faixas), Exportar.

### 13a. Aprendizado → base

- `GET /api/gestor/aprendizado?de=&ate=&colaborador=&origem=` → `{"itens": [...registros da seção 7a com id, mais recentes primeiro, até 500], "contadores": {total, sugestao_ok, sugestao_editada, livre, ignoradas, com_sugestao, pct_ok, pct_editadas, pct_ignoradas}, "periodo": "<aprendizado.periodo>"}`. `ignoradas` = `livre` com sugestão; os `pct_*` são sobre `com_sugestao` (0 se nenhum).
- **Propostas para a base** (tabela `propostas`): `GET /api/gestor/propostas[?status=nova]` → lista `{id, em, tipo: faq|info|correcao|preco, perguntas, resposta, campo, faq_id, produto_id, preco_novo, promocao, validade, justificativa, exemplos, sugestao_id, atual, origem: cerebro|regras|vendedor|fonte|chat|gestor, status: nova|incorporada|descartada, fonte, evidencia, contradiz, fonte_id}`. `atual` = o que está na base hoje no alvo (info do campo, resposta do FAQ, `<produto>: <preço vigente>`), para a prévia. **`resposta` = texto FINAL publicável, voltado ao cliente; o porquê/dúvidas vão só em `justificativa`** (1.6.8). Tipo `preco` (1.6.8): `{produto_id, preco_novo: "R$ …", promocao?, validade?: AAAA-MM-DD, justificativa}` quando o vendedor informou preço diferente do cadastrado. **Destino estruturado (1.6.8):** cada proposta grava no campo certo do `negocio.json` — `preco` → `produtos[]`; `produto` `{nome, palavras, preco_novo?}` → item novo em `produtos[]` (id = slug do nome; nome repetido → descartada/409); `horario` `{horarios: {dia: [[HH:MM, HH:MM]…]}, resposta?}` → só os dias da proposta em `horarios` (`[]` = fechado) e, se `info.horario_atendimento` tinha texto, ele é trocado pelo `resposta` enviado (ou esvaziado, voltando ao gerado); `info` → `info.<campo>`; `faq`/`correcao` → `faq[]`. Cada item traz `destino` em palavras (ex.: `Cadastros → Produtos → Plano anual → preço: R$ 1.200 → R$ 670`), mostrado como **Vai alterar:** no formulário (atualiza enquanto o gestor edita). `nome`, `palavras`, `horarios` também na lista. `POST /api/gestor/propostas/gerar {"de"?, "ate"?}` (padrão: últimos 7 dias) gera agora e devolve `{"criadas": n, "propostas": [...]}`. Com cérebro LLM — o **cérebro da curadoria** (`cerebro_curadoria`, senão o principal; `max_tokens` 4096, timeout 3×) — ele lê os registros do período, os produtos (id, nome, preço vigente) e a base e devolve JSON `{"propostas": [...]}` (itens de FAQ/info novos, correções ou preços; resposta inválida → cai nas regras). Validação: `preco` precisa de produto existente e `preco_novo` no formato `R$ 670`/`R$ 1.200,00`; `faq`/`info`/`correcao` com marca de bastidor na `resposta` (seção 1, `limpar-bastidores`) são **descartadas**; nas regras, respostas com bastidor não entram nos grupos. Por regras: agrupa as respostas `livre`/`sugestao_editada` parecidas (similaridade ≥ 0,8) com 2+ ocorrências → proposta `faq` (perguntas = as mensagens do lead, resposta = a mais frequente). Não repete proposta `nova` nem FAQ já existente com a mesma resposta.
- `POST /api/gestor/propostas` (1.7.8) cria uma proposta escrita pelo gestor (1.7.8: na lista, `fonte` = URL ou nome do arquivo de onde a proposta veio, `evidencia` = trecho curto que a prova, `contradiz` = diverge da base hoje, `fonte_id` = o trabalho da seção 13c; vazios/`false`/`null` nas outras origens) (corpo = uma proposta: `tipo` e os campos do tipo; `perguntas` aceita texto com uma por linha; `origem` `chat` ou `gestor`, padrão `gestor`) pela mesma validação das propostas do cérebro (inválida ou com bastidor → 422; mesmo texto de uma `nova` ou de um FAQ → 409) e devolve `{ok, proposta}` com status `nova`.
- `POST /api/gestor/propostas/incorporar-lote {"itens": [{id, ...campos editados}]}` (1.7.8, 1 a 100 itens; senão 422) incorpora na ordem, cada uma como o `incorporar` abaixo; a que falha não desfaz as outras e volta em `erros`: `{ok: true, incorporadas: [ids], erros: [{id, erro}]}`. Na página: caixa de seleção em cada proposta nova, **Incorporar selecionadas** abre uma prévia única (para cada uma, o "Vai alterar" e como fica) e **Confirmar incorporação (n)** grava.
- `POST /api/gestor/propostas/{id}/incorporar {"perguntas"?, "resposta"?, "preco_novo"?, "promocao"?, "validade"?}` (vale o texto **editado** pelo gestor) grava no `negocio.json` pela mesma validação do `PUT /api/gestor/config` (`faq` → item novo `apr-<id>` com as perguntas da proposta; `correcao` → troca a resposta do `faq_id`; `info` → **acrescenta** uma linha a `info.<campo>` sem duplicar texto igual — passar de 2000 caracteres → 422; `preco` → com `promocao` ou `validade` grava `preco_promocao`/`promocao`/`promocao_ate` e mantém o `preco` normal, sem elas troca o `preco` e apaga a promoção) e marca `incorporada`. `resposta` vazia ou com marca de bastidor (faq/info/correcao) → 422 (`recado interno`); `preco_novo` fora do formato ou `validade` fora de `AAAA-MM-DD` → 422. Na página, **Revisar e incorporar** mostra os campos editáveis (preço/promoção/validade no tipo `preco`) e a **prévia** de como fica a base; o segundo clique (**Confirmar incorporação**) grava. `POST /api/gestor/propostas/{id}/descartar` → `descartada`. Proposta que não está `nova` → 409.
- Depois de incorporar, importar ou salvar, a página do gestor **relê** `GET /api/gestor/config` (nenhuma aba grava uma configuração velha; Cadastros, Base e Base consolidada mostram o dado novo sem entrar de novo).
- **Geração periódica** pela tarefa de tempo (`/api/tarefas/rodar` / ciclo de 30 s): `diario` = a cada 24 h, `semanal` = a cada 7 dias, contados da última geração (ou do registro de aprendizado mais antigo); `desligado` = nunca. Com cérebro LLM a chamada sai pelo trabalhador em segundo plano (nunca dentro do tick).
- Em qualquer linha do aprendizado, **Virar FAQ** abre o formulário do FAQ pré-preenchido (pergunta = mensagem do lead, resposta = o que o vendedor mandou).

### 13b. Base consolidada (1.6.8)

- `GET /api/gestor/base` → `{"texto": <exatamente o texto da base que o cérebro recebe (seção 14)>, "secoes": {negocio, horario, horario_gerado, info: {campo: texto}, faq: [{id, perguntas, resposta}], produtos: [{id, nome, preco, preco_vigente, preco_promocao, promocao, promocao_ate, promocao_ativa}]}, "conflitos": [{tipo, alvo, mensagem}]}`.
- **Conflitos por regra** (sem LLM), `alvo` = `faq:<id>` | `info:<campo>` | `produto:<id>`: `horario` — FAQ de horário (pergunta sobre horário ou resposta com janela de horas) ou `info.horario_atendimento` cujos dias/horas divergem dos `horarios` (faixa `segunda a sexta`/`todos os dias`/`24h` compara a semana inteira; dia avulso só precisa estar aberto; "não abrimos aos domingos" não conta; ex.: "segunda a sexta, das 8h às 18h" × seg–dom 00:00–23:59 → `dias diferentes e horas diferentes`); `preco` — FAQ/info que cita um produto e `R$` diferente do preço normal e do promocional ativo; `promocao_vencida` — `preco_promocao` com `promocao_ate` antes de hoje; `faq_contraditoria` — a mesma pergunta (normalizada) em itens com respostas diferentes; `faq_duplicada` — itens com a mesma resposta; `bastidor` — info/FAQ com marca de bastidor (seção 1). Na página, cada conflito tem **editar**, que abre o campo (Base de conhecimento ou Cadastros).
- `GET /api/gestor/base.md` (Markdown legível: horário, informações, FAQ, produtos, conflitos e o texto exato) e `GET /api/gestor/base.json` (`{versao: 1, negocio, info, faq, produtos}` com as promoções), como anexo.
- `POST /api/gestor/base/importar` com o JSON (`info`, `faq` e/ou `produtos`; sem nenhum → 422): valida como o `PUT /api/gestor/config` (inválido → 422, nada muda) e devolve a **prévia** `{"ok": true, "aplicado": false, "mudancas": [{onde: "info.<campo>"|"faq.<id>"|"produtos.<id>", antes, depois}]}` sem gravar. `?aplicar=1` grava (só as chaves enviadas), com backup `negocio.json.<AAAAMMDD-HHMMSS>.bak` antes, e devolve `aplicado: true, backup`. Exportar e importar de volta sem editar = nenhuma mudança.

- **Chat da base** (1.7.8): `POST /api/gestor/base/perguntar {"pergunta": "...", "historico"?: [{de: gestor|base, texto}]}` [G] (pergunta 1–1000 caracteres; `historico` lista; senão 422) → `{resposta, fontes: [{secao, trecho}], lacuna, contradicao, proposta, conflitos: [{indice, tipo, alvo, mensagem}], origem: cerebro|regras}`. Com cérebro LLM usa o **principal** (não a curadoria) com o texto da base (seção 14), as últimas 6 falas do histórico e a lista de conflitos por regra; instrução: responder SÓ com o que está na base, citando a seção (`Produtos`, `FAQ: <pergunta>`, `Informações: <campo>`, `Horários`); sem resposta na base, começar por `Isso não está na base.` e devolver `lacuna: true` + `proposta` `{tipo: faq|info|produto|preco, perguntas, resposta?, campo?, nome?, preco_novo?, produto_id?}` (resposta vazia quando a base não traz o fato; marca de bastidor é apagada); contradição em `contradicao`. No anthropic vai `output_config.format = {type: json_schema, schema}` com `{resposta, fontes, lacuna, contradicao, proposta}` (todos obrigatórios; sem lacuna, `proposta.tipo = ""`); leitura tolerante nos outros (texto livre = resposta, sem fontes). `conflitos` = os da seção 13b cujo `alvo` é de uma seção citada (conflito de horário entra quando `Horários` é citado); `indice` = posição na lista de `GET /api/gestor/base`. Sem cérebro LLM, ou se ele falhar/recusar: **busca por palavras** (palavras significativas, como o FAQ, ≥ 34 % sobre o horário, os campos de `info`, os itens do FAQ e os produtos com suas palavras; pergunta de horário → `Horários`; produto casado → `Produtos`), até 4 trechos, `resposta` = `Encontrei na base:` + os trechos; nada casou → `lacuna: true`, `proposta: {tipo: faq, perguntas: [pergunta], resposta: ""}`. Nada é gravado (o histórico fica só na tela). Na página: caixa de conversa na aba Base consolidada; na lacuna, **Criar proposta** abre o formulário pré-preenchido e editável (tipo e campos do tipo) que grava pelo `POST /api/gestor/propostas` (`origem: chat`); **ver conflito** leva ao conflito da lista.

### 13c. Gerar base a partir de link ou arquivo (1.7.8)

- `POST /api/gestor/base/fonte {"url": "http(s)://...", "max_paginas"?: 8}` [G]: `max_paginas` inteiro 1–20 (padrão 8); URL só `http`/`https`, com host, sem usuário/senha, até 2000 caracteres; host que é IP literal interno recusa já aqui; inválido → 422. `POST /api/gestor/base/arquivo {"nome": "x.docx", "conteudo_base64": "..."}` [G]: extensões `txt`, `md`, `csv`, `html`/`htm`, `docx`, `pdf` (outra → 422); base64 inválido → 422; mais de **10 MB** → 413 (só esta rota aceita corpo até 14 MB). PDF que não começa com `%PDF` → 422; PDF sem cérebro da curadoria `anthropic` ligado e sem `pdftotext` no servidor (`ATENDE_PDFTOTEXT_BIN` muda o caminho) → 422 `PDF precisa do cérebro Anthropic ou do pdftotext`. Já com 3 leituras em andamento → 429. Resposta `{ok, fonte: <trabalho>}`.
- **Trabalho em segundo plano** (tabela `fontes`, só metadados): `GET /api/gestor/base/fontes` → `{fontes: [{id, em, tipo: link|arquivo, fonte, status: lendo|analisando|pronto|erro, paginas, caracteres, propostas, erro, avisos: [...]}], pdf: {anthropic, pdftotext}}` (30 mais recentes; no trabalho `pronto`, o último aviso diz a origem: `propostas pelo cérebro` ou `propostas pelas regras`). Um trabalhador próprio (não atrasa as sugestões) processa um por vez, com rede e cérebro fora do lock. Trabalho que estava `lendo`/`analisando` quando o servidor parou vira `erro` (`interrompido`) ao subir. O conteúdo (bytes e texto) fica **só em memória** e é descartado ao fim; o PDF para o `pdftotext` vai a um arquivo temporário apagado na hora. Nada fica guardado além das propostas e dos metadados.
- **Link:** baixa a página e as do **mesmo domínio** (host igual, `www.` ignorado) ligadas a partir dela, em largura, até profundidade 2 e `max_paginas` páginas com texto; ignora links para imagens/arquivos e `#fragmento`. **Proteção SSRF:** a cada pedido (inclusive cada redirecionamento, no máximo 3) resolve o host e recusa se **qualquer** endereço for privado, loopback, link-local, reservado, multicast, não especificado ou não global (`ipaddress`; IPv4 mapeado em IPv6 conta como IPv4) — mensagem com `interno`; conecta no IP já conferido (sem segunda resolução). 10 s e 2 MB por página (maior → a página é pulada, aviso com `2 MB`); só `text/html`/`text/plain`; `robots.txt` do host (`Disallow` do grupo `*`) respeitado; User-Agent `atende-leads (+<url_publica>)`. A primeira página que falhar põe o trabalho em `erro`; as outras viram `avisos`. Redirecionamento para outro domínio é pulado. `ATENDE_FONTE_PERMITIR_LOCAL` (**só teste, nunca em produção**): lista de `host:porta` liberados apesar de internos, ou `1` para todos.
- **Texto do HTML** (`html.parser`): remove `script`, `style`, `nav`, `footer`, `noscript`, `svg`, `template`, `iframe`, `form`, `head` (o `<title>` vira a primeira linha `# título`); títulos `h1`–`h6` como `#`…, itens de lista com `- `, linhas de tabela com as células separadas por ` | `; `meta description` entra. **DOCX** por `zipfile` + `word/document.xml` (parágrafos; tabelas com ` | `; DTD/entidade → recusa). TXT/MD/CSV/HTML decodificados (UTF-8, senão cp1252).
- **Propostas** pelo **cérebro da curadoria** (seção 14): o texto vai em blocos de ~15 mil caracteres (no máximo 12; o resto vira aviso), cada um marcado `=== Fonte: <url ou arquivo> ===`, com a base atual, os produtos (id, nome, preço vigente) e os ids do FAQ; instrução: só fatos do conteúdo, sem bastidor, não repetir o que a base já tem, `contradiz: true` quando diverge da base. Saída `{propostas: [{tipo: info|produto|preco|horario|faq|correcao, perguntas, resposta, campo, nome, palavras, horarios (texto `seg 08:00-18:00; dom fechado`), faq_id, produto_id, preco_novo, promocao, validade, justificativa, fonte, evidencia, contradiz}]}` com `output_config.format` json_schema no anthropic (todos os campos obrigatórios) e leitura tolerante nos outros. **PDF com curadoria anthropic:** uma chamada só, com o PDF como bloco `document` (seção 14). As propostas de todos os blocos são juntadas e validadas como na seção 13a (tipo, produto existente, `R$`, campo, horários válidos; bastidor descartado) e **descartadas** quando a base já diz o mesmo (preço igual ao normal ou à promoção ativa, texto já contido no campo `info`, horário igual, FAQ com a mesma pergunta, correção igual); repetidas (mesmo tipo, alvo e texto) viram uma; até 40 por trabalho. `fonte` fora das fontes lidas → a URL inicial/o nome do arquivo; `evidencia` até 300 caracteres; `contradiz` também é `true` em `preco`, `correcao` e `horario` sobre dia já cadastrado. Entram `nova`, `origem: fonte`, `fonte_id` = o trabalho, e seguem a revisão de sempre (seção 13a). Cérebro sem resposta em todos os blocos → regras.
- **Sem cérebro LLM** (regras), só o óbvio: telefones (até 3) e e-mails (até 3) → `info.observacoes` (`Telefone: …`, `E-mail: …`); a primeira linha com CEP → `info.endereco`; `R$` com o nome antes na linha (ou a linha anterior curta) → `preco` se o nome contém um produto cadastrado, senão `produto`; linhas com dia e horas (`segunda a sexta, das 7h às 19h`) → uma proposta `horario`; link lido e `info.site` vazio → `info.site` = a origem.
- Página (Base de conhecimento → **Importar de link ou arquivo**): link + nº de páginas, **Enviar arquivo**, lista dos trabalhos (status, páginas, caracteres, propostas, avisos, erro) que se atualiza sozinha enquanto há leitura, aviso ao terminar e **Revisar no Aprendizado**. No Aprendizado, a proposta de fonte mostra a fonte (link), a evidência e o selo `contradiz a base`.

## 14. Cérebro do agente

- `regras` (padrão): tudo da seção 4. **Resumo** do chamado = até 3 linhas montadas por regra: `Quer: <produto ou assunto>`, `Urgência: <hoje/este mês/pesquisando>` (se respondeu), `Disse: "<última mensagem, até 120 caracteres>"`.
- `ollama` (`{"tipo": "ollama", "url": "...", "modelo": "..."}`) e `openai` (qualquer endpoint compatível com `/v1/chat/completions`; chave em `CEREBRO_API_KEY`, nunca no JSON; a chave só é enviada se o host de `cerebro.url` estiver em `CEREBRO_HOSTS_PERMITIDOS` — lista separada por vírgula de `host` ou `host:porta`; vazia = a chave não é enviada a ninguém —, porque quem tem o token do gestor pode mudar `cerebro.url`): usados **só** para (a) escrever o resumo, (b) responder dúvidas que caíram em "não entendi", (c) a sugestão à equipe (seção 7a) e (d) as propostas para a base (seção 13a), usando FAQ e produtos como base, com instrução de não inventar preço/prazo. Timeout de 15 s; erro, timeout ou resposta vazia → cai na regra. A chamada roda **fora** do lock do banco (a transação lê o necessário, solta o lock, chama e grava numa transação curta). As decisões de abrir chamado continuam sendo as da seção 4 (podem ser acrescidas por uma classificação do cérebro com saída `pediu_humano|venda|precisa|nada`).
- **Base de conhecimento** = o contexto que todo cérebro LLM recebe: nome do negócio, `info` (com o horário gerado se vazio), FAQ e produtos (com preço ou `sem preço informado`). **Instrução de sistema**: português do Brasil, curto e cordial, usar só a base, nunca inventar preço/prazo/condição; se não souber, dizer que vai chamar alguém da equipe (no "não entendi" a instrução pede `SEM_RESPOSTA`, que cai na regra e o sistema chama alguém). Usado para: resumo, dúvida que caiu em "não entendi", sugestão (seção 7a, com instrução própria) e propostas (seção 13a, com instrução própria e o cérebro da curadoria). **Atendente na conversa (1.6.8):** na dúvida respondida pelo agente (não entendi ou enquanto espera alguém assumir), se o lead já tem mensagem de vendedor, vão as últimas 10 mensagens da conversa e a mesma ordem de verdade da seção 7a (o que o vendedor afirmou vale sobre a base; o último valor vale).
- **Cérebro da curadoria** (`cerebro_curadoria`, seção 2): mesmo formato de chamada do tipo escolhido, `max_tokens` 4096, timeout 3× o do tipo. Chave: `CEREBRO_CURADORIA_API_KEY` se definida (outro provedor), senão `CEREBRO_API_KEY`. Padrão sugerido na página quando o tipo é `anthropic`: `claude-opus-5-5` com esforço `medium` (sem `thinking`).
- `anthropic` (`{"tipo": "anthropic", "modelo": "claude-sonnet-5-5", "esforco": "low"}`): `POST https://api.anthropic.com/v1/messages` (URL fixa; `CEREBRO_ANTHROPIC_URL` só para teste), headers `x-api-key: <CEREBRO_API_KEY>`, `anthropic-version: 2023-06-01`, `content-type: application/json`, `anthropic-beta: server-side-fallback-2026-07-01`; corpo `{model, max_tokens: 1024, system: [{type: text, text: <instruções>}, {type: text, text: <base>, cache_control: {type: ephemeral}}], messages, output_config: {effort: <esforco>}, fallbacks: "default"}` — **sem** `thinking`, `temperature`, `top_p`, `top_k` nem prefill de assistant. `esforco`: `low` (padrão) | `medium` | `high` | `xhigh` | `max`. Lê `content` só se `stop_reason != "refusal"`; usa o primeiro bloco `type == "text"`. Host sempre permitido para a chave (é fixo). Timeout 20 s.
- `openrouter` (`{"tipo": "openrouter", "modelo": "anthropic/claude-sonnet-5.5"}`): `POST https://openrouter.ai/api/v1/chat/completions` (fixo; `CEREBRO_OPENROUTER_URL` só para teste), `Authorization: Bearer <CEREBRO_API_KEY>`, `HTTP-Referer: <url_publica>`, `X-Title: atende-leads`; corpo OpenAI (`model`, `messages`, `max_tokens: 1024`). Host sempre permitido. Timeout 20 s.
- `claude_cli` / `codex_cli` (assinatura pessoal pelo CLI local, sem API): `claude -p --model <modelo, padrão sonnet>` e `codex exec -m <modelo> -s read-only --skip-git-repo-check -`, prompt pelo **stdin** (fechado), timeout 60 s, fora do lock, numa pasta temporária vazia; saída = stdout sem espaços nas pontas. Binário: `CEREBRO_CLI_BIN` (padrão `claude`/`codex`). Só funciona rodando direto na máquina (`./atende serve`) com o CLI logado; no Docker o binário não existe.
- **Anexo PDF** (1.7.8, só curadoria `anthropic`, seção 13c): `messages[0].content` vira a lista `[{type: document, source: {type: base64, media_type: application/pdf, data}}, {type: text, text: <pergunta>}]`.
- `modelo` (todos os tipos LLM): só letras, dígitos e `.:/@_-`, até 100 caracteres, sem começar com `-` (→ 422). A chave nunca vai no JSON (→ 422).
- **Disponível?** `anthropic`/`openrouter` sem `CEREBRO_API_KEY` ou sem `modelo`, `ollama`/`openai` sem `url`/`modelo`, CLI sem o binário no `PATH` → `cerebro_ok: false` com `cerebro_motivo` na saúde (seção 18), e tudo segue por regras. Erro, timeout, recusa ou resposta vazia → regra, como sempre. `CEREBRO_TIMEOUT_S` (só teste) baixa os timeouts.
- Os testes rodam com `regras` e com servidores/binários falsos locais; nenhum teste chama serviço real.

## 15. WhatsApp pela Evolution API

Variáveis: `EVOLUTION_URL`, `EVOLUTION_API_KEY`, `EVOLUTION_INSTANCIA`, `WEBHOOK_SEGREDO`. Sem `EVOLUTION_URL` → canal simulado (só caixa de saída, `status: "simulado"`).

- **Entrada** `POST /webhook/evolution/{WEBHOOK_SEGREDO}` (segredo errado → 404). Formato Evolution v2: `{"event": "messages.upsert", "instance": "...", "data": {"key": {"remoteJid": "5541999990001@s.whatsapp.net", "fromMe": false, "id": "ABC"}, "pushName": "Maria", "message": {"conversation": "oi"}, "messageType": "conversation"}}`. Sempre 200. Ignora: outro `event`, `fromMe: true`, grupo (`@g.us`), `key.id` repetido. **`remoteJid` terminado em `@lid`** (identificador oculto do WhatsApp): o telefone vem de `key.remoteJidAlt` (Evolution 2.3+), `key.senderPn` ou `data.senderPn`, o primeiro que existir; sem nenhum, a mensagem é descartada e registrada em `descartes` (seção 13). O telefone do `remoteJid` já vem com o código do país: fica só com os dígitos (8 a 15), **sem** acrescentar `55`. Texto = `message.conversation` ou `message.extendedTextMessage.text`; sem texto → responde `Por enquanto só consigo ler mensagens de texto.` `pushName` vira nome sugerido (usado como `nome` só se o lead não tiver nome **e** depois de confirmar na qualificação — a pergunta do nome passa a ser `Posso te chamar de <pushName>?`; `sim` aceita, outra resposta vira o nome).
- **Saída:** `POST {EVOLUTION_URL}/message/sendText/{EVOLUTION_INSTANCIA}`, header `apikey`, corpo `{"number": "<dígitos>", "text": "..."}`, na ordem por telefone. O envio é **assíncrono**: a mensagem entra na caixa de saída como `pendente` e o despachante entrega fora do lock (a requisição que a gerou espera até ~2 s pelo despacho, fora do lock).
- `GET /api/saida` [G] → caixa de saída `[{id, telefone, texto, tipo: agente|humano|aviso, status: enviado|pendente|simulado|falhou|cancelado|web, em}]`. `pendente` (erro HTTP/conexão) é reenviado com **backoff exponencial** por mensagem (5, 10, 20… s, teto 300 s; ~10 min no total), no máximo **8 tentativas** → `falhou`; até 20 mensagens por rodada. A tarefa de tempo acorda o despachante (`POST /api/tarefas/rodar` também adianta o backoff). Lead com `nao_contatar` não recebe reenvio (`cancelado`). `web` = mensagem a lead do chat web (seção 4).

## 16. Telegram

Variáveis: `TELEGRAM_API_URL` (ex.: `https://api.telegram.org`), `TELEGRAM_TOKEN`, `TELEGRAM_GRUPO_ID`, `TELEGRAM_SEGREDO`, `TELEGRAM_MODO` (`webhook`, padrão, | `polling`). Sem elas, nada vai ao Telegram e o resto funciona (painéis web).

- **Modo de recebimento.** `webhook` (padrão): o Telegram chama `POST /webhook/telegram` (precisa de domínio público com HTTPS e do `setWebhook`). `polling` (máquina sem domínio, teste local): ao subir, o servidor chama `deleteWebhook` com `drop_pending_updates: false` e uma thread faz `getUpdates` com long polling (`timeout` = `TELEGRAM_POLL_TIMEOUT`, padrão 25 s; `allowed_updates` = `message` + `callback_query`; `offset` = último `update_id` tratado + 1, gravado no SQLite na mesma transação do tratamento, para não reprocessar depois de reiniciar). Cada update recebe o **mesmo tratamento** do `POST /webhook/telegram` (sem o header de segredo, porque vem direto do Telegram); update que quebra o tratamento vai para `descartes` e o offset avança. Erro de rede/HTTP no `getUpdates`: espera 1, 2, 4… até 30 s e tenta de novo, sem derrubar o servidor; `409 Conflict` (webhook ativo) → `deleteWebhook` de novo. A chamada de rede não segura o lock do banco. A thread para quando o servidor para. Funciona também no modo `ATENDE_AGORA`. Em `polling`, `TELEGRAM_SEGREDO` não é exigido (nem pela trava de `0.0.0.0` da seção 1); sem ele, `POST /webhook/telegram` responde 401.

- Envios **assíncronos** pela caixa de saída do Telegram (mesmas regras de ordem por destino e backoff da seção 15; erro 4xx não é repetido). O `message_id` devolvido pelo Telegram é gravado depois, numa transação curta, e usado nas edições e nos replies. Depois de enviado (ou `falhou`), o texto não fica guardado na fila. Edições do painel fixo são **coalescidas** (só o último texto sai).
- Chamadas: `POST {TELEGRAM_API_URL}/bot{TOKEN}/<método>` com JSON: `sendMessage` (`chat_id`, `text`, opcional `reply_markup.inline_keyboard`, `reply_to_message_id`), `editMessageText` (`chat_id`, `message_id`, `text`, `reply_markup`), `answerCallbackQuery` (`callback_query_id`, `text`), `pinChatMessage`, `getFile` (áudio); no modo `polling`, também `deleteWebhook` e `getUpdates`.
- `POST /webhook/telegram` exige header `X-Telegram-Bot-Api-Secret-Token: {TELEGRAM_SEGREDO}` (senão 401). Sempre 200 com segredo certo.
- **Vínculo:** no privado, `/entrar <codigo>` liga o `from.id` do Telegram ao colaborador (responde `Olá, <nome>!` e mostra os botões de status `🟢 Livre` / `🔴 Ocupado` / `⚫ Fora`). Código errado → `Código inválido.`; 5 códigos errados do mesmo `from.id` em 1 minuto → `Muitas tentativas, aguarde.` (mesmo com o código certo) até a janela passar. Se o colaborador já estava vinculado a outro `from.id`, o vínculo passa ao novo e o anterior recebe no privado um aviso (contém `outra conta`). Mensagens e botões de quem não está vinculado → `Envie /entrar <seu código>.` O vínculo persiste. Mensagens privadas vão ao `chat_id` = `from.id` vinculado; colaborador sem vínculo não recebe ofertas (é pulado na ordem de vez, sem contar como recusa) — exceto se o Telegram não estiver configurado, quando a oferta fica só no painel web.
- **Botões** (`callback_data`, até 64 bytes): `as:<id>` assumir, `pa:<id>` passar, `st:livre|ocupado|fora`, `fe:<id>:<resultado>` fechamento, `fm:<id>:<motivo>` motivo, `fr:<id>:<1|3|7>` retorno em N dias às 09:00, `fp:<id>` pular nota, `dv:<id>` devolver, `lc:<id>` continuo, `lt:<id>` terminei, `ra:<id>` assumir retorno, `sg:<id>:ok` enviar sugestão, `sg:<id>:ed` editar sugestão, `sb:<id>` atualizar a base com o conflito da sugestão (seção 7a, 1.6.8). Toda `callback_query` recebe `answerCallbackQuery`.
- **Comandos** (privado do vinculado): `/livre`, `/ocupado`, `/fora`, `/status`, `/meus` (chamados dele), `/retornos` (retornos de hoje), `/lead <nome ou telefone>` (ficha curta, só de leads que ele pode ver), `/fechar <id> vendeu <valor>` | `/fechar <id> retornar <AAAA-MM-DDTHH:MM>` | `/fechar <id> negociando` | `/fechar <id> sem <motivo>` | `/fechar <id> invalido <motivo>`. No grupo: só `/status`, e só no grupo da equipe (`chat.id == TELEGRAM_GRUPO_ID`); em qualquer outro grupo o bot não responde nada.
- **Privacidade:** no grupo, nunca telefone nem texto das mensagens do lead; só primeiro nome, motivo, nota, interesse e tempos.

## 17. Docker / VPS

- `Dockerfile` (`python:3-slim` ou similar, sem `pip install`) rodando `./atende serve --host 0.0.0.0 --porta 8080 --dados /dados`, com `HEALTHCHECK` em `/api/saude`, como **usuário não-root** (uid/gid 1000; `/dados` do host precisa ser desse uid: `chown -R 1000:1000 dados`). `.dockerignore` deixa fora da imagem `.env`, `dados/`, `tests_dev/`, `.git/`, `guia/`, `capa/`.
- `docker-compose.yml`: serviço `atende` (`build: .`, `restart: unless-stopped`, `env_file: .env`, volume `./dados:/dados`, porta `127.0.0.1:8080:8080`). Perfil `evolution` (`docker compose --profile evolution up -d`) com a Evolution API v2 e o que ela exige na versão atual (banco e cache), na mesma rede, porta só em `127.0.0.1`. Por LGPD a Evolution não guarda cópia de mensagens, contatos, conversas, etiquetas nem histórico: todos os `DATABASE_SAVE_*` = `"false"`, exceto `DATABASE_SAVE_DATA_INSTANCE` (a sessão do WhatsApp).
- `.env.exemplo` com todas as variáveis das seções 14–16 (exemplos, nenhum segredo real), com `EVOLUTION_URL=` e `TELEGRAM_TOKEN=` **vazios** (integrações desligadas até preencher) e os segredos de webhook com `troque` (recusados em `0.0.0.0` se a integração for ligada sem trocar). Também documenta `ATENDE_PROXY_CONFIAVEL`, `ATENDE_MAX_CONEXOES` e `ATENDE_PERMITIR_EXEMPLO`.
- `instalar-vps.sh`: confere Docker, pergunta nome do negócio, domínio, token do Telegram, grupo e o modo do Telegram (`webhook`, padrão, ou `polling`), gera segredos aleatórios (token do gestor e **códigos da equipe** com `secrets.token_urlsafe(9)` ou mais, trocando os do exemplo e os curtos), escreve `.env` e `dados/negocio.json` com `umask 077` (só o dono lê) — rodando de novo, **reaproveita** os segredos que já estão no `.env` (`WEBHOOK_SEGREDO`, `TELEGRAM_SEGREDO`, `EVOLUTION_API_KEY`, `EVOLUTION_DB_SENHA`, `CEREBRO_*`, `WHISPER_CMD`; gera só os que faltam ou contêm `troque`) e diz quais na saída —, passa `dados/` ao uid 1000 (`chown`, como root; sem ser root, `sudo -n chown`; se `dados/` continuar de outro uid, **aborta antes de subir** com o comando a rodar), sobe o compose (com ou sem Evolution), instala **um único** cron de backup (`docker compose exec -T atende ./atende backup ...` copiado para fora do volume de dados, `/opt/atende-leads-backups` criado com `install -d -m 700`, arquivo com `chmod 600`) e imprime o token, os códigos e os próximos passos (proxy HTTPS, túnel SSH para o manager da Evolution e o QR, `setWebhook` do Telegram — só no modo `webhook` —, backup e restauração). `--sem-perguntas` usa variáveis de ambiente (para teste).
- README com **Deploy na VPS** e **O processo, do início ao fim**.
